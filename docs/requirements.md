# KnowledgeHub 第一版需求草案

状态：阶段 1 需求整理，尚未完成阶段边界确认。

更新日期：2026-10-26。

## 1. 项目目标与工作区

构建面向企业内部员工的知识库问答系统，覆盖制度与技术资料。员工只能检索有权访问的文档，回答应提供可核查的来源；证据不足时明确说明资料不足。

- 目标项目源目录：`E:\KnowledgeHub\knowledgehub-app`。
- 参考项目目录：`E:\KnowledgeHub\enterprise-serviceops-agent`，仅供学习，不修改、不覆盖。
- 开发采用边做边讲的方式，每次推进一个明确任务，解释设计并执行适当验证。
- 当前仅整理需求，不创建业务代码。参考项目的语法检查结果不代表目标项目已实现或通过测试。

## 2. 已确认的业务范围

1. 知识类型：公司制度与技术知识混合。
2. 样本来源：编写模拟企业资料，不依赖真实企业文档。
3. 文档访问范围：全员、指定部门，以及额外的跨部门共享。
4. 敏感等级：L1、L2、L3，分别用 1、2、3 表示；第一版必须实现。
5. 访问必须同时满足部门范围与敏感等级要求。跨部门共享不能绕过等级限制。
6. 权限由后端强制执行，不能由用户提交的身份字段或 Prompt 决定。
7. 项目按可独立完成、可测试和可部署的完整应用设计，控制复杂度；只为当前功能保存必要字段，不提前设计任务平台或复杂恢复机制。

## 3. 第一版建议边界与待确认事项

以下为当前建议，不视为已经逐项确认的业务决定：

| 项目 | 建议 | 状态 |
| --- | --- | --- |
| 问答方式 | 单轮问答，每次问题独立；后续增加多轮会话 | 待确认 |
| 管理角色 | 一个系统管理员负责上传和授权，员工负责查询；暂不增加部门管理员 | 待确认 |
| 员工部门 | 每位员工属于一个部门 | 待确认 |
| 部门文档 | 每份文档设置一个默认允许访问的部门，可额外共享给多个部门 | 待确认 |
| 开发交互 | 先通过 FastAPI 接口文档操作，暂不开发前端 | 待确认 |
| 文档格式 | 入库阶段统一交付 Markdown、TXT、DOCX、文字型 PDF；逐个实现和验证解析器 | 已确认本次设计方向 |

四种格式共用上传、清洗、分片、Embedding 和存储流程，区别在解析器。第一版不包含扫描件 OCR；遇到扫描件或无法可靠提取的内容应明确提示，不得静默当作完整入库成功。混合文字与扫描页面的 PDF 如何检测和拒绝，在解析阶段验证。

管理员的管理范围、阅读权限以及是否允许绕过文档访问规则，需要在角色设计时明确；不能仅凭“管理员”称呼自动给予读取所有内容的权限。

## 4. 权限规则

员工可以检索文档，必须同时满足：

1. 已登录且账号有效。
2. 文档已成功完成索引，可供检索。
3. 用户访问等级大于或等于文档敏感等级。
4. 文档不限制部门，或用户属于默认允许部门，或用户所属部门在额外共享范围内。

“全员”仅表示不限制部门，仍需检查账号和敏感等级。

权限检查覆盖文档列表、详情、问答检索、引用查看，以及后续如提供的原文件下载。不可访问的片段不得进入模型上下文或响应。检索服务只能返回成功入库的文档；管理界面需要允许授权管理者查看处理中的文档及失败状态。

### 权限相关数据设计草案

此处记录讨论方向，正式字段类型、约束和迁移在阶段 2 决定。

| 表 | 职责 | 关键字段方向 |
| --- | --- | --- |
| users | 员工身份与访问资格 | id、department_id、access_level、is_active；管理角色字段待定 |
| departments | 统一维护部门 | id、name |
| documents | 文档信息与访问规则 | id、title、access_department_id、classification_level、status |
| document_department_shares | 额外跨部门共享关系 | document_id、department_id |

- 建议使用共享关系表替代部门 ID 数组，以便使用外键和组合唯一约束。
- `access_department_id` 为空表示不限制部门，此时不配置额外共享关系。
- 用户与文档等级均限定为 1～3，且不允许为空。
- 上述四张表并非完整数据库设计，文档片段、向量和其他业务字段后续补充。

## 5. 文档入库需求

处理流程：

```text
授权管理者上传文件并设置访问范围、敏感等级
  → 校验文件格式、大小和授权范围
  → 保存文档记录并标记处理中
  → 解析、清洗、切分文本
  → 调用 Embedding 服务
  → 保存片段、来源元数据与向量
  → 标记可检索；失败则记录失败状态与可排查原因
```

要求：

- 不支持或超出大小限制的文件应返回明确错误，具体大小上限待定。
- 只有成功完成入库的文档能够参与检索，避免部分入库结果被误用。
- 可查看文档列表与处理状态。
- 失败不能伪装成成功；状态及重试方案在阶段 2 细化。
- PDF 页码、Markdown 标题等来源定位信息应尽可能保留，不能编造不存在的页码。

## 6. 知识问答需求

```text
接收并校验问题
  → 从后端认证信息取得用户身份和权限
  → 生成查询向量
  → 在有权访问、已完成索引的文档中检索片段
  → 判断证据是否充分
      → 不充分：返回资料不足
      → 充分：基于证据生成答案 → 校验引用 → 返回答案和来源
```

要求：

- 检索服务先独立实现和测试，再接入 LangGraph。
- 引用必须对应本次实际检索且用户有权访问的片段。
- 返回文档名称、引用片段及可用的定位信息。
- 引用 ID 存在不等于答案有依据，评估还应检查答案与引用内容是否一致。
- 模型、Embedding 或数据库调用失败应给出可识别的服务错误，不能冒充“资料不足”。
- 不使用联网搜索补充企业资料中不存在的事实。

## 7. 模拟资料与验收案例

建议样本包括《差旅报销制度》《请假与审批流程》《内部系统部署手册》《常见故障排查指南》。需准备不同部门、不同等级，以及有共享和无共享的样本；具体内容后续编写。

| 场景 | 预期结果 |
| --- | --- |
| 文档写明差旅报销须在返回后 30 天内提交，用户询问期限 | 回答 30 天并引用对应原文 |
| 问题在可访问资料中没有充分依据 | 明确说明资料不足，不编造答案 |
| L2 技术部员工查询技术部 L2 文档 | 可以检索并返回对应引用 |
| L2 技术部员工查询未共享的人事部 L1 文档 | 该文档片段不进入模型上下文或响应 |
| 人事部 L2 文档共享给技术部，L2 技术部员工提问 | 可以检索 |
| 技术部员工为 L2，已共享文档为 L3 | 仍不可检索 |
| 全员范围文档为 L3，用户为 L1 | 不可检索 |
| 用户账号停用或未登录 | 请求被拒绝 |
| 文档解析或索引失败 | 管理者可见失败状态，文档不参与检索 |
| 模型生成的引用不属于本次检索结果 | 不作为有效引用返回；失败处理策略阶段 2 定义 |

以上均为待实现、待执行的验收标准，不是已通过的测试结果。

## 8. 技术边界

- FastAPI：HTTP 接口、请求校验、认证接入和响应。
- 普通业务服务：解析、分片、Embedding、检索、模型调用与数据库操作。
- LangGraph：问答步骤和条件分支编排，不替代业务服务。
- PostgreSQL + pgvector：业务数据、文档片段和向量检索。
- Docker：应用和数据库的可重复运行环境。
- 文档表第一版保留 11 个字段，详见数据库设计。文件大小在上传时校验，不要求持久化；暂不做文件去重、处理阶段细分和自动任务恢复。
- Embedding 模型、维度和分片参数统一放在应用配置中，不逐文档记录。更换 Embedding 模型时必须统一重新入库，不能继续混用旧向量。
- SQLAlchemy、Alembic、Pydantic、pytest 等具体版本和用法，在实现前结合环境及官方文档确认。
- Redis：后续有明确使用场景再接入。
- Checkpoint、多轮会话、长期记忆、多 Agent、复杂监控与分布式任务系统不提前引入。
